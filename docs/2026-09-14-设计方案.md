## 1. 文档定位

本文档定义 ABIS 管理控制台 **前端骨架** 的建设方案，供骨架实现与后续开发拆分使用。

本文档**不是**需求文档。《ABIS-GUI管理平台需求分析》已冻结功能范围与字段定义，本文档只解决一个需求文档未回答的问题：

> **在管理 API 契约尚未冻结的前提下，前端如何开工，且如何在契约冻结后不返工。**

## 2. 范围

## 3. 系统形态与部署边界

### 3.1 纯静态 SPA，无自有后端

管理控制台是 **纯 API 消费者**。依据：

- 需求引言·集成方式："管理控制台**不直接访问**数据库、算法服务或内部节点。控制台账户数据、权限校验与审计留痕均落在 ABIS 侧。"
- 需求 1.1："控制台账户数据、权限校验与审计留痕均落在 ABIS 侧。"

因此**构建产物是静态资源**（HTML / JS / CSS），由 Nginx 直接发布，不引入新的常驻服务进程。这一条约束了技术选型——任何需要常驻 Python/Node 服务的 UI 框架（NiceGUI、Streamlit、Reflex 等）均不符合本形态。

### 3.2 入口隔离

需求 3.1 要求管理控制台入口与 ABIS 业务 API **分离**（独立路径或独立端口），不得混用同一入口地址。

- 业务 API 现有前缀为 `/abis/{feature}/...`；
- 本方案建议管理 API 使用 **`/abis-admin/...`** 前缀；
- **路径前缀 vs 独立端口由部署侧最终裁定**，属契约草稿的待澄清项。

### 3.3 部署位置

依据需求·部署前提，ABIS GUI 与 ABIS 服务同机部署于应用服务器（2 台裸金属，与 Nginx、Keepalived、HAProxy、ABIS Gateway、ABIS System、模板提取同机）。

前端构建产物交由该机 Nginx 发布，**不需要额外的运行时**。

## 4. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 构建工具 | Vite | Vue 生态标准构建工具，配置少、启动快 |
| 框架 | Vue 3（Composition API） | 中文企业后台最主流；中文文档与社区资源最厚 |
| UI 组件库 | Element Plus | 表格 / 表单 / 抽屉 / 确认弹窗 / 分页开箱即用，与企业后台形态高度匹配 |
| 路由 | Vue Router | 官方路由，用于页面切换与角色守卫 |
| 状态管理 | Pinia | 官方状态库，用于登录态与监控轮询状态 |
| HTTP | axios | 与 Element Plus 生态常规搭配，拦截器便于统一处理会话失效 |
| 语言 | JavaScript + JSDoc | **不用 TypeScript**，见下 |

### 4.1 为何不用 TypeScript

ABIS 后端开发团队为 **Python 栈**（依据《自研ABIS部署计划-团队传达版》："全 Python 栈：开发同事 Python 为主，不熟 Java"）。前端骨架将来大概率由同一批人或其接手者维护。

TypeScript 会增加类型系统的学习与配置负担，而本工程的类型需求（接口报文字段）用 **JSDoc 注释 + 集中式常量定义** 已可覆盖。选型偏向"能被人接手"而非"工程上最优"。

> 若后续确定由专业前端团队接手，可再评估迁移 TypeScript。Vue 3 对渐进式引入 TS 支持良好。

## 5. 信息架构与页面清单

### 5.1 页面清单（6 项）

| 序号 | 页面 | 路由 | 需求出处 | 核心内容 |
| --- | --- | --- | --- | --- |
| 1 | 登录 | `/login` | 1.1 | 本地账户 + 密码；空闲超时；登录成功/失败均入审计 |
| 2 | 服务状态监控（首页） | `/monitor` | 1.3 | 六监控对象、四态、算法四项指标；1 分钟轮询 |
| 3 | 匹配阈值配置 | `/threshold` | 1.2 | 人脸 / 指纹 1:N 阈值；1–100 整数；二次确认；生效延迟提示 |

│            │                                      │
│  ● 服务状态 │                                      │
│  ○ 阈值配置 │            页面内容区                 │
│  ○ 账户管理 │                                      │
│  ○ 日志查询 │                                      │
│  ○ 审计查询 │                                      │
│            │                                      │
└────────────┴──────────────────────────────────────┘

**首页即服务状态监控**——需求 1.3 是唯一有轮询行为的页面，作为落地页最符合运维人员的使用动线。

## 6. 角色与权限

### 6.1 权限矩阵（需求 1.1）

| 功能 | 管理员 | 运维员 |
| --- | :---: | :---: |
| 服务状态查看 | ✓ | ✓ |
| 日志与审计查询、导出 | ✓ | ✓ |
| 匹配阈值修改 | ✓ | ✗ |
| 账户创建 / 修改 / 禁用 / 删除 | ✓ | ✗ |
| 审计记录操作 | 只读 | 只读 |

### 6.2 前端实现方式

- 权限矩阵集中定义在 `src/constants/roles.js` 单一文件；
- 路由守卫按矩阵拦截直接输入 URL 的访问；
- 侧边导航按矩阵隐藏无权限项；
- 页面内写操作入口（按钮）按矩阵禁用或隐藏。

### 6.3 强调：前端控制不是安全边界

需求 A.2 明确："两级固定角色的权限须在 **ABIS 侧强制校验，不能仅由界面控制**。"

前端的角色控制**只是体验优化**，不构成安全措施。本文档的实现不改变这一事实，契约草稿中亦将角色校验列为 ABIS 侧必做项。

## 7. 数据访问层设计（核心）

### 7.1 解决的问题

管理 API 的请求 / 响应结构尚未冻结（附录 A.1 中 8 个接口全部标注"路径与报文字段待定"）。若页面直接调用接口，契约冻结时需修改散布于各页面的调用点，返工面不可控。

### 7.2 方案：可替换适配器

页面**不直接调用 HTTP**，只调用一层中间层。该层暴露统一的函数签名，底层有两个实现：

```
        ┌──────────────────┐
页面 ──▶ │   src/api/index  │
        └────────┬─────────┘
                 │  按 VITE_USE_MOCK 选择
        ┌────────┴─────────┐
        ▼                  ▼
  adapters/mock.js   adapters/http.js
   （当前使用）        （契约冻结后启用）
```

**切换机制**：环境变量 `VITE_USE_MOCK`。

| 取值 | 行为 |
| --- | --- |
| `true`（默认） | 走 mock 适配器，返回本地生成的数据 |
| `false` | 走 HTTP 适配器，请求真实管理 API |

**关键性质**：切换适配器时，**页面代码零改动**。返工被限制在 `src/api/adapters/http.js` 一个文件内。

### 7.3 接口契约的代码化

`src/api/contract.js` 用 JSDoc 定义每个接口的函数签名与报文字段，作为**前端侧的唯一真源**。两个适配器都必须实现该签名。

这样做的附带收益：该文件本身就是契约草稿的代码化表达，可直接对照生成《管理 API 契约草稿 v0》。

## 8. 管理 API 接口清单

《需求分析》附录 A.1 将管理 API 列为 **8 条**（登录认证、账户管理、阈值读取、阈值写入、聚合健康查询、调用日志查询、审计记录查询、数据导出）。下表将其拆解为**具体的 HTTP 端点**——例如"登录认证"一条在实现上需要登录、登出、会话校验三个端点，"账户管理"需要列表与增删改等多个端点。

**因此：下表 11 行对应需求文档的 8 条，不是新增了能力，只是同一条能力落到端点粒度。**

**路径与报文字段均为建议值**，出自《需求分析》附录 A.1 及正文对应章节，最终以 ABIS 侧冻结结果为准。

| # | 接口 | 建议路径 | 方法 | 需求出处 |
| --- | --- | --- | --- | --- |
| 1 | 登录 | `/abis-admin/auth/login` | POST | 1.1 |
| 2 | 登出 | `/abis-admin/auth/logout` | POST | 1.1 |
| 3 | 会话校验 | `/abis-admin/auth/session` | GET | 1.1 |
| 4 | 账户列表 / 创建 | `/abis-admin/accounts` | GET / POST | 1.1 |
| 5 | 账户修改 / 禁用 / 删除 | `/abis-admin/accounts/{id}` | PUT / DELETE | 1.1 |
| 6 | 密码重置 | `/abis-admin/accounts/{id}/password-reset` | POST | 1.1 |
| 7 | 阈值读取 / 写入 | `/abis-admin/thresholds` | GET / PUT | 1.2 |
| 8 | 聚合健康查询 | `/abis-admin/health` | GET | 1.3 |
| 9 | 调用日志查询 | `/abis-admin/logs` | GET | 1.4 |
| 10 | 审计记录查询 | `/abis-admin/audits` | GET | 1.4 / 2.2 |
| 11 | 数据导出 | `/abis-admin/{logs\|audits}/export` | GET | 1.4 |

### 8.1 登录与会话

- 初版为本地账户 + 密码认证，不预留对接 SIGATT 统一认证（需求 1.1）；
- 密码须以加盐哈希存储——**属 ABIS 侧实现要求**，前端不接触；
- 会话应有空闲超时（需求 1.1）；
- **会话凭据的传递方式正文完全未规定**（token 还是 cookie、放 header 还是 body），属待澄清项。

### 8.2 聚合健康查询

需求 1.3 已确认在 ABIS 侧**新增一个聚合健康接口**，由该接口采集全部监控对象，前端仅调用此单一接口。

- 前端**不直连**任何内部节点；
- 初版只需输出各监控对象的健康状态 + 算法服务运行指标；
- 不要求输出集群主备归属与实例拓扑（需求 B.3）；
- 不要求覆盖 Nginx / Keepalived / Patroni / etcd / HAProxy（需求 B.4）。

### 8.3 阈值接口

- 仅两类：人脸 1:N 去重阈值、指纹 1:N 去重阈值；
- 取值范围 **1–100 的整数**（上限 100 为产品设定值）；
- 不含 Top-N，不含 1:1 核验判定阈值（后者归 SIGATT 业务系统）；
- 变更须记录操作人、时间、变更前后值并纳入审计（需求 1.2）。

## 9. Mock 数据来源

**mock 数据不做任何发明**，每个字段都从需求文档已冻结的表格反推。

| mock 模块 | 字段来源 | 生成规模 | 说明 |
| --- | --- | --- | --- |
| 审计记录 | 需求 2.2 的 10 字段 | 数十条 | 覆盖登录/登出、账户变更、阈值变更三类 |
| 调用日志 | 需求 1.4 的 6 字段 + 5 过滤维度 | 数百条 | 数量需足以验证分页与筛选 |
| 监控状态 | 需求 1.3 的六对象 + 四态 + 四项指标 | 六对象各一条 | **必须含一个 MinIO「未部署」样本** |
| 账户 | 需求 1.1 的两级角色 | 若干条 | 含禁用态账户样本 |
| 阈值 | 需求 1.2 的 1–100 整数 | 人脸 / 指纹各一个 | 默认值取实际生产合理值 |

### 9.1 字段清单（供 mock 与契约对照）

**审计记录（需求 2.2，10 字段）**

时间、操作人、角色、操作类型、操作对象、变更前值、变更后值、结果、来源 IP、会话 ID

**调用日志（需求 1.4，6 字段）**

调用时间、调用方标识、接口、生物模态、结果状态、处理耗时

**调用日志的 5 个过滤维度**

时间范围、接口、生物模态、结果状态、耗时区间

**监控对象（需求 1.3，六项）**

ABIS Gateway、ABIS System、Face 算法服务、Fingerprint 算法服务、PostgreSQL、MinIO

**监控状态四态**

正常 / 异常 / 不可达 / 未部署

**算法服务运行指标（需求 1.3，四项）**

`cdc.healthy`、`cdc.ready`、`gallery.total_size`、`license.status`（VALID / INVALID）

**日志覆盖的五个业务接口（需求 1.4）**

| 接口 | 方法 | 路径 |
| --- | --- | --- |
| Biometric Comparison（比对） | POST | `/abis/{feature}/comparison` |
| Biometric Verification（核验） | POST | `/abis/{feature}/verification` |
| Biometric Identification（1:N 识别） | POST | `/abis/{feature}/identification` |
| Biometric Add（注册 / 更新） | PUT | `/abis/{feature}` |
| Biometric Delete（删除） | DELETE | `/abis/{feature}/{userId}/{delType}/{uuid}` |

健康检查 `GET /abis/{feature}/health` **不纳入调用日志**（需求 1.4）。

### 9.2 mock 数据的两条硬约束

1. **不得包含生物图像数据。** 需求 1.4 以 danger 框明确：调用记录不得包含请求报文中的 base64 人脸 / 指纹图像。mock 同样遵守，避免将来有人照着 mock 结构去实现。
2. **「未部署」不能表现为「不可达」。** 需求 1.3 明确：MinIO 未部署时必须呈现为「未部署」，不触发异常标识。mock 需能驱动界面区分这两态。

## 10. 需求遗留问题的界面处置

需求文档存在三处未决或自相矛盾之处。前端在不擅自定论的前提下，做兼容性设计。

### 10.1 阈值下限的双语义矛盾

**冲突事实**：ABIS 接口协议对低于生效下限（指纹 40、人脸 60）的阈值，两处表述互斥——参数表写"按 40 默认处理"（**纠正**），错误码 4000005 写"请传入正确的阈值"（**拒绝**）。需求 1.2 已核实并明确要求：

> "澄清前界面**不得按任一种语义写死提示文案**。"
> "不得出现界面显示值与实际生效值不一致且无任何提示的情况。"

**本方案的处置**：

- 两套提示文案（纠正语义 / 拒绝语义）**同时写出**，集中定义在 `src/constants/threshold.js` 单一常量中；
- 界面按当前接线的那一套渲染，另一套以注释保留并标注 `TODO: 待协议澄清后二选一`；
- 澄清结论落地时，**只改这一个文件**。

**注意**：现有澄清项只覆盖了"调用方传入低于下限的值"这一路径。**控制台写默认值**这条路径未被覆盖，须一并澄清——已列入 §11。

### 10.2 监控实例粒度不自洽

**冲突事实**：

- 需求 1.3 监控对象表：Face / Fingerprint 算法服务"实例数 2（合并部署）"；
- 需求·部署前提：2 台算法 VM，人脸与指纹**合并部署在同一算法虚拟机**内。

按部署前提推算，2 台 VM × (人脸 + 指纹) = **4 个服务实例**；而监控表写的是 **2**。界面应渲染 2 行还是 4 行，文档未自洽。

**本方案的处置**：

- 界面**按需求 1.3 表格渲染**（六监控对象，算法服务各一行）；
- 但数据结构按"**可扩展为按实例展开**"组织，即在监控对象下预留 `instances[]` 层；
- 裁决落地后，若需按实例展开，**只改渲染层，数据层不动**。

### 10.3 「未部署」态的判定来源

需求 1.3 要求聚合健康接口输出「未部署」状态值，但**该状态的判定来源无出处**——ABIS 侧依据什么判定 MinIO 是"未部署"而非"不可达"，文档未定义。

**本方案的处置**：mock 直接产出该状态值，界面对四态等价处理；判定来源列入 §11 待澄清。

| 5 | 错误码风格与错误响应结构 | 阻塞错误处理 | ABIS 侧 |
| 6 | 导出触发方式（同步下载 / 异步任务）与单次导出量上限 | 阻塞导出实现 | ABIS 侧 |
| 7 | 日志埋点层次（ABIS Gateway / ABIS System） | 决定日志内容与量级 | ABIS 侧 |
| 8 | 监控实例粒度（2 还是 4） | 决定监控页渲染行数 | 双方，见 §10.2 |
| 9 | 「未部署」态的判定来源 | 决定聚合健康接口实现 | ABIS 侧，见 §10.3 |
| 10 | 阈值下限（指纹 40 / 人脸 60）的取得方式 | 阻塞阈值页校验逻辑 | 双方 |
| 11 | 阈值下限的处置语义（纠正 / 拒绝），**含控制台写默认值路径** | 阻塞阈值页文案 | 双方，见 §10.1 |
| 12 | 会话空闲超时时长 | 阻塞前端超时处理 | 双方 |
| 13 | 账户删除后，其历史审计记录的操作人如何存续 | 影响审计展示 | ABIS 侧 |
| 14 | 批量导入（约 200 万条 Add）是否豁免日志 | 影响日志容量与查询 | 双方 |
| 15 | X-Forwarded-For 是否透传 | **不约定则审计「来源 IP」全记为代理地址** | 部署侧 |

> **第 15 项需特别留意**：需求 2.2 将「来源 IP」列为审计字段，而审计是追责依据。若 Nginx / HAProxy 未透传真实来源地址，该字段将失去证据价值。此事项需求文档全篇未提及。

## 12. 验证方式

本工程是**原型骨架**，非交付代码，因此不编写单元测试与端到端测试。

验证改为**可运行验收**：

1. `npm install && npm run dev` 能在本地启动；
2. 逐页走查 6 个页面，确认字段与需求文档一致；

4. 确认监控页四态可区分，尤其 MinIO 的「未部署」不显示为异常；
5. 确认日志与审计页的筛选、分页、详情、导出按钮可用（导出走 mock 生成的 CSV）。

上述走查过程将截图留档。

## 15. 附：对客口径差异提示

《ABIS-GUI管理平台原始需求》是唯一 `provenance: human` 的文档，即对客承诺。相对该文档，内部《需求分析》有三处收窄：

| 项 | 对客原文 | 内部口径 |
| --- | --- | --- |
| 角色模型 | 基于角色的访问控制（RBAC） | 两级固定角色 |
| 监控刷新 | 实时展示 | 1 分钟固定周期轮询 |
| 异常告警 | "支持异常状态告警提示" | 界面状态高亮与异常标识，**不做外发告警** |

前两项已被《需求分析》§4 偏离表记录。**第三项未被记录**——对客原文的"告警提示"可被客户理解为外发告警（邮件 / 短信 / Webhook），而需求 1.3 明确初版不做外发。

**建议**：在《需求分析》§4 偏离表补记该项，以免验收时缺少书面依据。此事不阻塞本工程，但与本工程的交付口径相关。
