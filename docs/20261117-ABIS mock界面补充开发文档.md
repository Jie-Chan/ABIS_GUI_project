# ABIS Mock 界面补充开发文档

版本日期 2026-11-17

本补充接续 [[20261116-ABIS mock界面开发文档]]，用于本轮申请人指纹数量说明、请求耗时及主列表分页的开发。与原文档相应规则有差异时，按本补充执行。

## 1. 申请人指纹数量文案与行高

申请人列表移除指纹缩略图上方独立的数量或状态说明行，包括「10/10 指」「6/10 指」「8/10 指」「指纹未入库」等文案及其占位。指纹仍按固定十指位置显示，已入库图像、未入库占位、图像不可用状态及各指位的悬停提示按原文档执行。去重后的有效指位数继续用于业务数据及入库变更记录。

申请人详情的图像分区标题统一显示「指纹」，省去标题旁的「10 指」「8 指」「0 指」等数量。手别、指位名称、质量分和图像预览按原文档展示。

数量行移除后，同步收紧指纹组内的间距及行内上下留白。申请人列表行高以人脸缩略图、指纹图像和操作入口完整可读为准，随实际内容确定。桌面十指横排与窄屏左右手分组换行时，均核对图像、占位及操作完整可见。

## 2. 请求耗时单行展示

### 2.1 统一时间单位

「请求耗时」列统一使用 `ms`、`s`、`min`、`h`，数值与单位之间留一个空格。已完成与尚未结束的请求使用同一格式。

| 耗时范围 | 显示示例 |
| --- | --- |
| 不足 1 秒 | `320 ms` |
| 1 秒至不足 1 分钟 | `1.25 s` |
| 1 分钟至不足 1 小时 | `6 min 40 s` |
| 1 小时及以上 | `1 h 6 min 40 s` |

秒级数值最多保留两位小数，省去末尾多余的零。分钟及小时格式中的秒显示整数。小时累计超过 24 后继续增加，例如 `27 h 3 min 18 s`。缺少有效起止数据时显示「—」，实际为零时显示 `0 ms`。

### 2.2 表格与详情

日志列表移除「已用时」辅助行，耗时单元格只显示单行数值及单位。请求是否完成由「执行状态」和「响应发布状态」表达。进行中的数值变化时保持单元格及行高稳定。

按最长样例分配耗时列宽，并采用禁止换行的样式。核对 `320 ms`、`6 min 40 s`、`1 h 6 min 40 s` 均完整可读。列宽不足时通过表格已有横向滚动访问完整列，固定操作列保持可用。

请求详情沿用「请求总耗时」及进行中「已用时」的字段含义，取值统一采用本节单位格式。ABIS 接口处理耗时使用相同的格式化规则及其独立计时口径。

## 3. 后端计时与前端刷新

### 3.1 时间字段与完成条件

后端提供请求接收时间、当前状态及已确认的完成时间，列表响应同时提供本次计算所用的服务端时间。以下字段为对接示例，复用现有等价字段。

| 字段 | 含义 |
| --- | --- |
| `receivedAt` | 服务端记录的请求接收时间。 |
| `responseSentAt` | 同步请求最终响应发送完成时间。 |
| `publishedAt` | 异步请求最终响应发布得到确认的时间。 |
| `serverTime` | 本次列表响应对应的服务端时间。 |

时间统一采用带时区的 ISO 8601 表示，起止时间使用一致的计时基准。已完成请求也可直接返回按相同口径计算的毫秒耗时，前端使用服务端确认值。

| 场景 | 请求总耗时 |
| --- | --- |
| 同步请求已完成 | `responseSentAt − receivedAt`，固定显示。 |
| 异步请求最终响应已发布确认 | `publishedAt − receivedAt`，固定显示。 |
| 等待处理、处理中、等待重试 | 从接收时间累计到当前服务端时刻。 |
| 执行成功或失败，最终响应待发布 | 继续累计到最终响应发布确认。 |
| 待人工核查、执行结果未知 | 继续表示请求尚未闭环的累计等待时间。 |

ABIS 接口处理耗时取已确认的独立起止记录，缺少有效记录时显示「—」。请求超时及进入人工核查时，依据已确认的业务状态展示。

### 3.2 前端累计与校准

首次查询时，未结束请求以 `serverTime − receivedAt` 得到计时基数。前端记录收到结果时的单调时钟读数，每秒根据实际经过时间更新单元格，刷新间隔内使用以下计算方式。

```text
当前展示耗时 = 本次查询的计时基数 + 收到结果后实际经过的时间
```

可使用 `performance.now()` 计算浏览器内的经过时间，避免客户端系统时间与服务端不一致、用户调整系统时间等情况影响展示。[浏览器单调时钟说明](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now)

查询结果中存在未结束请求时，复用现有读取接口定期更新状态及校准计时基数，可先按 5～10 秒的间隔对接。前端每秒的数字变化在本地完成。收到最终响应完成信息后，立即按后端确认的完成时间或耗时固定显示。

自动更新继续使用当前已生效的查询条件、排序及分页，保留表格滚动位置和详情上下文。筛选输入尚未提交时，沿用原文档的查询与导出规则。晚到的旧查询响应应丢弃，已完成状态以本次有效响应为准。

接口读取失败时保留上次确认的数据，停止本轮本地递增，并通过页面已有错误反馈说明数据暂未更新。恢复连接或页面从后台重新激活后先重新查询、校准，再恢复尚未结束请求的计时。导出耗时以服务端生成导出结果时的统一时点计算，单位格式与本补充一致。

## 4. 验收要求

1. 用 `U001`、`U004` 和无有效指纹申请人核对列表，确认独立数量说明行及占位已移除。十指图像或缺采占位、指位顺序、悬停状态和详情入口完整可用。详情仅显示「指纹」标题，质量分及放大预览正确。
2. 在 `1440 × 900`、`1280 × 720` 和 `624 × 850` 核对数量行移除后的列表。检查图像、行内留白和左右手换行，确认行高随内容收紧，固定表头与分页可用。
3. 分别用 320 ms、1250 ms、400000 ms、4000000 ms 和超过 24 小时的测试值核对格式。检查缺失值「—」及实际零值 `0 ms`。
4. 核对正常完成、处理中、待发布和待人工核查的请求耗时均为单行。包含 `1 h 6 min 40 s` 的记录完整可读，数值变化时表格行高保持稳定，固定操作列可用。
5. 用 `REQ-00000012` 核对业务成功、响应待发布时继续计时，用 `REQ-00000008` 核对待人工核查的累计等待时间。通过测试接口将异步记录切到已发布，确认耗时固定为后端完成时间差。同步请求完成后也固定显示。
6. 改变测试客户端系统时间，核对展示仍依据服务端计时基数。让标签页在后台停留后返回，确认先重新读取并校准，已完成请求停止递增。模拟读取失败及恢复，核对数据反馈和计时恢复。
7. 在计时及状态自动更新期间切换分页、排序和详情，确认查询上下文保留。编辑筛选但暂不提交时，列表及导出仍对应已生效条件。核对导出中所有未结束请求使用同一服务端时点计算耗时。

## 5. 主列表分页统一

### 5.1 适用范围与显示规则

申请人列表、日志查询、审计查询和账户管理的主列表采用相同的每页条数选项、首次默认值及分页控件样式。

| 项目 | 统一要求 |
| --- | --- |
| 每页条数选项 | 按 `10`、`20`、`50`、`100` 升序排列，四页保持一致。 |
| 首次默认值 | 当前会话尚无该页选择记录时，默认 `20 条/页`。 |
| 选中值文案 | 统一为 `10 条/页`、`20 条/页`、`50 条/页`、`100 条/页`，数值后留一个空格。选择框显示当前实际使用的每页条数。 |
| 控件外观 | 四页的条数选择框使用相同宽度、高度、字号及内边距，并与页码按钮垂直居中。 |
| 分页区顺序 | 从左到右依次为「共 N 条」、每页条数选择框、上一页、页码、下一页，整组在底部右对齐。 |

结果总数采用当前已生效查询的总条数，仅显示一次。少量结果及零条结果仍保留完整的四档选项，当前选中值保持实际每页条数。日志查询、审计查询的「导出 CSV」沿用底部左侧位置，与右侧分页同排。其他页面的既有底部操作按原文档执行。

### 5.2 切换与会话恢复

改变每页条数后，立即按新条数读取第 1 页，保留当前已生效的筛选条件和排序。尚未提交的筛选输入继续保持编辑状态，本次条数切换使用已生效条件。选择框、实际请求的每页条数和返回记录保持一致；末页或结果不足时显示实际返回条数。

同一登录会话内，四个页面分别记住本页最近选择的每页条数。从其他导航项返回时恢复本页选择。用户在某页调整条数后，其他页面继续保留各自的选择。首次默认值仅用于该页尚无会话记录的情况。

日志查询已有的筛选、排序、页码和滚动位置恢复规则继续按原文档执行。日志计时和状态自动更新期间，保持当前每页条数及分页上下文，按本补充 §3.2 刷新数据。

### 5.3 验收要求

1. 在新的登录会话中首次进入四个主列表，核对均默认 `20 条/页`。展开下拉框，确认四页的选项、顺序和文案完全一致。
2. 使用超过 100 条的测试数据，分别选择 `10`、`20`、`50`、`100`，核对实际查询条数及每页结果。已有筛选、排序或处于后续页时改变条数，确认回到第 1 页，已生效条件与排序保持不变。另编辑筛选但暂不提交，确认条数切换仍使用已生效条件。
3. 分别将申请人、日志、审计和账户管理设为不同条数，切换导航后逐页返回，确认各自选择保留。日志自动刷新、进入详情及返回时，核对每页条数和原有分页上下文保持正确。
4. 分别核对零条、不足 10 条、刚好一页和多页结果，确认总数准确且只出现一次，四档选项完整，当前选中值正确，末页无重复或遗漏记录。
5. 在 `1440 × 900`、`1280 × 720` 和 `624 × 850` 核对四页底部选择框的尺寸、字号、排列及对齐。分页和既有底部操作完整可用，下拉菜单的四档选项均可访问，横向滚动表格时底部分页保持可见。

## 6. 日志查询表格移除处理环节列

日志查询表格移除「处理环节」列的标题、单元格内容及其占位宽度，列内附属提示随单元格一并移除。桌面、紧凑桌面及窄屏布局均执行该规则。其余列按现有顺序排列，「执行状态」「响应发布状态」「请求耗时」及「详情」入口正常显示。

本次调整范围为日志查询表格。请求详情页保持现有内容与布局，包括「处理过程」、异常信息及各页签。

验收时在 `1440 × 900`、`1280 × 720` 和 `624 × 850` 核对表头、记录和横向滚动区域，确认「处理环节」列及其空白占位已移除，其余列对齐且详情入口可用。分别打开 `REQ-00000008`、`REQ-00000011` 和 `REQ-00000012`，核对详情展示与调整前一致。

## 7. 日志 Mock 全量展示与检索

### 7.1 默认查询范围

日志查询默认覆盖当前完整的 Mock 请求数据，包括既有 15 条演示请求、预置申请人的历史注册、删除与重采记录及补充验收请求。首次进入或重置查询后，完整数据均参与列表展示和检索。原文档中默认仅展示 15 条、输入申请人 ID 或请求 ID 后才纳入历史及补充样例的范围约定，由本节替代。

Mock 适配器取消依据 `historical` 标记排除默认查询记录的判断。申请人 ID、请求 ID、时间范围、接口类型、生物模态、执行状态和响应发布状态等筛选，均作用于完整数据集。可以仅用时间范围、接口类型或状态等条件直接检索历史及补充记录。

当前默认场景共 45 条请求，底部总数按实际匹配结果统计。先对完整数据集筛选、排序，再分页。首次进入仍默认按接收时间倒序、每页 20 条，当前 45 条数据对应 3 页，依次展示 20、20、5 条。每页条数及会话恢复按本补充 §5 执行。

### 7.2 列表与导出一致性

列表、总数、分页和 CSV 导出共用同一份已生效查询条件及完整数据范围。CSV 覆盖该查询的全部分页。编辑筛选但尚未点击「查询」时，导出继续对应上一次已生效结果。

申请人图像、入库变更记录和请求日志继续使用同一套 Mock 业务数据，以申请人 ID 关联人员，以请求 ID 精确关联具体请求。从入库变更记录点击「查看日志」时，按携带的申请人 ID 和请求 ID 定位到该次请求。

原文档中按默认 15 条样例计算的列表、筛选及 CSV 数量，改为按完整数据集计算。页面沿用现有筛选栏、表格和底部分页区，通过底部总数与分页浏览完整结果。

### 7.3 验收要求

1. 使用默认 Mock 场景，在新登录会话中首次进入日志查询，核对共 45 条、每页 20 条，按接收时间倒序排列。逐页核对 20、20、5 条，请求 ID 无重复或遗漏。重置后重新覆盖完整数据范围。
2. 保持申请人 ID 和请求 ID 为空，选择覆盖 `U301`、`U302` 历史记录的时间范围并查询，确认可直接检索历史注册、删除和重采请求。另组合接口类型、模态或状态，核对筛选作用于完整数据集。重置后分别按接口类型查询，当前数据中的注册、1：N查重和删除依次为 27、12、6 条。
3. 分别按 `U001`、`U004`、`U201` 和 `U301` 查询，核对已有请求与历史注册记录均可找到。默认数据下，`U001` 为 4 条，`U004` 为 3 条，`U201` 为 1 条，`U301` 为 7 条。从申请人入库变更记录跳转，确认仍只显示所选的具体请求。
4. 全量查询后导出 CSV，核对数据记录为 45 条，并覆盖全部分页。提交筛选后核对列表总数与导出数据记录数一致。仅编辑筛选但暂不提交，确认导出仍对应上一次已生效结果。
