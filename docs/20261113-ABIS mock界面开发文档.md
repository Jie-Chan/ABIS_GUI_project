# ABIS Mock 界面开发文档

版本日期 2026-11-13

本次更新接续 [[20261112-ABIS mock界面开发文档]]，按界面分章记录日志查询、申请人列表、服务状态监控和审计查询的开发要求及验收项。本轮开发范围包括第 1、2、4 章查询页的筛选栏吸附、第 2 章申请人列表和 Mock 日志联动，以及第 3 章服务状态页排版。监控页沿用现有「监控」下拉菜单、监控数据及交互。

## 1. 日志查询界面

### 1.1 查重图像比对

查重请求的「图像比对」使用独立标签页。抽屉的标签顺序和默认页见 §1.5。

「图像比对」左侧展示原始图像，右侧展示选中的候选图像。图像下方分别标注各自的用户 ID。候选排名和接口实际返回的比对分数放在右侧图像上方，可与「候选图像」标题同一行展示。指纹案例在左右图像标题旁分别标注对应指位，例如「左手食指」。两侧图框保持等高并采用紧凑间距，图框高度随「图像比对」标签页的剩余空间调整，为图像下方的用户 ID 预留完整一行。图像等比完整显示，在 1422 × 804 和 1280 × 720 的桌面视口首屏同时看到两张图像、用户 ID、分数及指纹指位。候选按钮按本次响应中的顺序排列，文案仅显示「候选 1」「候选 2」等序号。候选用户 ID 显示在右侧图像下方。切换候选时保留左侧图像。

本阶段沿用现有图像存储，通过 GUI 后端按用户 ID 查询 ABIS PostgreSQL 中的 MinIO 图像链接，再获取图像供界面展示。左侧用户 ID 取本次请求的待查对象 `userId`，右侧取本次查重响应中对应候选的 `userId`。按请求的生物模态以及已有的部位信息定位对应图像。Mock 使用本地虚构数据模拟该取图过程。

查重明确完成且候选列表为空时，左侧照常展示可获取的原始图像，右侧居中显示「本次查重无候选」。两侧保持一致的背景和间距，右侧采用低对比度的空状态图标和中性文字。尚未取得明确查重结果时，右侧显示「暂无查重结果」。

用户记录或图像链接缺失时，在对应图像位置显示「暂无可用图像」。确认对象已删除时显示「图像已删除或不存在」，临时读取失败时显示「图像加载失败」。保留对应用户 ID 和本次响应记录的候选信息。

图像页顶部显示简短提示「图像根据当前用户记录获取，可能与本次查重时的图像不同；已删除的图像可能无法显示。」

> [!warning] 历史图像一致性
> 此方案按用户 ID 查询当前 ABIS 数据库和 MinIO 中的图像。请求对象或候选对象更新图像后，历史查重记录可能展示更新后的图像。用户记录、图像链接或 MinIO 对象删除后，历史记录中的对应图像可能无法读取。本次查重的候选和分数仍取原响应，图像仅供辅助查看。

### 1.2 请求列表字段与接口类型

请求 ID 列放在用户 ID 列前面，依次作为列表第一列和第二列。每条请求都有请求 ID，用户 ID 缺失时显示「—」，该请求仍可通过请求 ID 查询并打开详情。

在「接收时间」后增加「请求来源 IP」列，显示发起这条业务请求的调用方 IP。同步请求使用 ABIS 接收请求时记录的原始调用方 IP。异步请求使用上游随请求传递并记录的原始发起方 IP。MQ Broker、适配服务和重试节点的 IP 属于处理链路信息。原始发起方 IP 未记录或无法确认时显示「—」。Mock 使用虚构 IP 覆盖同步、异步及缺失三种样例。

查重接口的界面名称统一为「1：N查重」。接口类型筛选项显示「1：N查重」，匹配指纹和人脸两种模态。列表和抽屉中保留模态，显示「指纹 1：N查重」或「人脸 1：N查重」。

### 1.3 处理环节名称与展示

将请求列表的「当前阶段」列改名为「处理环节」。列表显示中文名称，Stage 英文代码在抽屉中展开对应阶段后展示。列表与抽屉的阶段标题使用同一套中文名称。

| Stage 代码 | 中文名称 | 含义 |
| --- | --- | --- |
| `ADAPTER_RECEIVED` | 接收请求 | 适配服务接收请求并可靠保存任务。 |
| `ADAPTER_CALLING` | 调用 ABIS | 适配服务发起调用并等待 ABIS 响应。 |
| `ABIS_HANDLING` | ABIS 处理 | ABIS 执行注册、查重、删除等业务。 |
| `ADAPTER_RESPONDED` | 发布结果 | 适配服务保存结果并发布到响应 MQ。 |

「处理环节」沿用既有阶段选择规则。处理中优先显示阻塞任务执行或响应交付的环节，正常完成后显示最后完成的环节。发生异常时显示需要关注的环节，业务失败且失败响应已交付时显示「ABIS 处理」。执行状态和响应发布状态分别说明业务执行结果及响应交付情况。

异步阶段顺序显示为「接收请求 → 调用 ABIS → 发布结果」，「ABIS 处理」位于对应调用尝试内部。同步请求显示「ABIS 处理」。注册、查重、删除由接口类型表达。

### 1.4 多候选查重案例

在原有 13 条请求后追加以下两个异步查重案例，共展示 15 条请求。每个新增案例返回 3 名候选，使用本地虚构图像和响应数据，执行成功且响应已发布。

| 请求 ID | 待查用户 ID | 接口类型 | 按响应顺序返回的候选用户 ID | 业务结果摘要 |
| --- | --- | --- | --- | --- |
| `REQ-00000014` | `U009` | 指纹 1：N查重 | `U101`、`U102`、`U103` | 查重成功 · 候选 3 条 |
| `REQ-00000015` | `U010` | 人脸 1：N查重 | `U201`、`U202`、`U203` | 查重成功 · 候选 3 条 |

两个案例均提供可正常读取的待查对象图像和三名候选图像。指纹案例采用同一指位的原始及候选指纹，沿用已有指位标识；人脸案例提供原始及候选人脸图像。按现有 Mock 接口的分值范围配置三名候选的递减示例分数，候选 ID、排名、分数和图像关联在响应 JSON 与「图像比对」页中保持一致。

进入「图像比对」页时默认选中排名第一的候选，候选按钮显示「候选 1」「候选 2」「候选 3」及当前选中状态。逐一切换时，右侧图像、用户 ID、排名和分数随之更新，左侧待查图像及其用户 ID 保持可见。两个案例均显示已有的历史图像风险提示。

### 1.5 抽屉信息表格与分区

抽屉标题统一使用「请求详情」。顶部信息表格与下方详情区等宽、左右对齐，中间留约 20 px 间距。表格使用细浅边框和浅色字段背景，保持紧凑行距。

异步请求的信息表格按以下顺序排布。通栏行的字段名占左侧标签格，内容合并右侧三格。

| 行 | 左侧字段与内容 | 右侧字段与内容 |
| --- | --- | --- |
| 1 | 请求 ID，通栏展示 | 合并至左侧内容 |
| 2 | 用户 ID | 接口类型，包含模态及同步／异步标识 |
| 3 | 接收时间，通栏展示完整日期及毫秒 | 合并至左侧内容 |
| 4 | 执行状态 | 响应发布状态 |
| 5 | 请求总耗时；进行中的请求按既有口径显示「已用时」 | ABIS 接口处理耗时 |
| 6 | 业务结果摘要，通栏展示 | 合并至左侧内容 |

同步请求的信息表格省去响应发布状态，耗时仅展示请求总耗时。同步的请求总耗时与 ABIS 接口处理耗时按同一口径计算。字段按剩余空间紧凑排列。移除旧「ABIS 实际处理耗时」及业务处理 Event 中对应的单独用时数值（如 `120 ms`）。业务处理 Event 保留起止时间、结果和异常信息。

下方详情区使用浅色边框包住标签栏和当前页内容。标签栏位于详情区顶部。查重请求依次显示「处理过程｜接口报文｜图像比对」，其他请求依次显示「处理过程｜接口报文」。打开抽屉默认进入「处理过程」，顶部信息表格在各标签页中均可见。选中项用主题色文字和下划线突出。标签栏背景与表格字段背景使用同一档浅灰色，内容区以白色为主，内部留约 16 px 边距。通过表格、间距和详情区边框形成上下分区。抽屉标题、表格字段和标签名称承担标题层级。

### 1.6 ABIS 接口报文

「接口报文」是独立标签页，设置「请求参数」「响应结果」两项。首次进入该标签页时两项默认展开，点击整行标题可分别展开或折叠。切换标签页时保留用户手动调整的展开状态。

「请求参数」展示实际发送给 ABIS 接口的请求正文，「响应结果」展示对应的 ABIS 响应正文。JSON 格式化显示，使用浅灰背景。请求参数和响应结果各自使用可滚动的代码区域，较长的正文在对应区域内滚动。

有多次 ABIS 调用尝试时，按尝试编号对应各次请求参数与响应结果。缺少已记录正文时，展开后分别显示「暂无请求参数记录」或「暂无响应正文记录」。Mock 为对应调用尝试补充本地虚构的请求参数和响应正文。

### 1.7 阶段默认展开方式

「处理过程」页直接展示阶段标题和时间线，省去额外的「阶段概览」标题。同步请求的单一「ABIS 处理」阶段直接显示接收请求、业务处理、发送响应三个 Event，标题右侧显示状态和耗时，下面显示阶段代码及紧凑起止时间。

首次打开请求详情时，所有顶层阶段默认展开。同步请求展开顶层「ABIS 处理」，异步请求展开「接收请求」「调用 ABIS」「发布结果」。异步「调用 ABIS」内嵌的「ABIS 处理」默认折叠，折叠行显示阶段名称、状态和耗时，点击后查看内部事件。各请求状态均采用同一规则，历史异常保留在对应 Event 中。

阶段采用紧凑的时间线行，左侧保留节点和连线，右侧的状态、耗时和展开箭头分别对齐。展开后显示时间和事件。调用方放在对应的接收请求事件详情中，生物模态由顶部接口类型表达，人工核查提示放在需要核查的状态旁。

用户可手动展开或折叠阶段，切换标签页后保留其选择。

顶部请求信息表格和标签栏固定在抽屉顶部。「处理过程」的时间线区域按当前窗口的剩余可用高度限制最大高度。内容超出时，仅时间线区域纵向滚动，鼠标指针位于时间线上即可用滚轮查看其余事件。内容较少时自然显示。

### 1.8 页面标题与紧凑筛选栏

移除页面内容区独立的图标、「日志查询」大标题和「按请求或用户追查处理阶段、事件与响应结果」说明文字。顶部导航通过高亮的「日志查询」标识当前页面，内容区从筛选栏开始。

桌面宽度下，筛选栏按以下顺序紧凑排列为两行，全部筛选条件默认可见。

| 行 | 第一列 | 第二列 | 第三列 | 右侧操作 |
| --- | --- | --- | --- | --- |
| 第一行 | 请求 ID | 用户 ID | 时间范围（开始时间至结束时间） | |
| 第二行 | 接口类型 | 生物模态 | 执行状态 | 查询、重置 |

两行共用列线。每列上下两个字段的标签左对齐，控件起点也对齐。字段名位于控件左侧并垂直居中，同一列的标签使用统一宽度。下拉框按选项文本设置紧凑宽度，ID 和时间范围按完整值的输入需要分配空间。查询和重置放在第二行最右侧，窄屏时控件按字段顺序自然换行，按钮跟在筛选条件之后。缩小筛选栏上下留白和行间距。

移除总耗时区间筛选。日志列表继续展示「请求耗时」列。

页面从上到下依次为顶部导航、两行紧凑筛选栏、请求数量及导出工具条、日志列表。组合查询和重置沿用现有行为。CSV 按当前筛选结果导出，移除「ABIS 实际处理耗时」列。

申请人列表、日志查询和审计查询共用筛选栏固定规则。筛选栏从页面打开时起固定在顶部导航下方。滚动列表时，筛选栏在视口中的纵向位置始终与首屏一致，当前条件和「查询」「重置」始终可操作。可将筛选栏放在列表滚动区域外，表格内容在筛选栏下方独立滚动。日期选择器和下拉菜单应完整展开。打开详情抽屉时，筛选栏位于遮罩下方。

三页均须在记录足够滚动时核对筛选栏的上边缘。分别记录首屏、刚开始滚动约 40 px、滚到列表中段及回到顶部的位置，确认上边缘的视口坐标一致，并确认表格记录确实发生滚动。

### 1.9 验收要求

核对查重请求依次显示「处理过程｜接口报文｜图像比对」，其他请求依次显示「处理过程｜接口报文」。确认默认进入「处理过程」，切换标签后顶部信息表格仍可见。核对左右图像及各自用户 ID。用 `U001` 的正常查重核对无候选空状态，用 `U002` 的查重核对候选 `U001` 的图像；结合 `U002` 已删除的样例核对左侧图像不可用时的展示。核对图像更新风险提示、图像缺失及加载失败状态，以及多名候选时的切换。

核对列表前两列依次为请求 ID、用户 ID。用户 ID 缺失的记录仍显示请求 ID，并可正常查询和打开详情。核对「接收时间」后一列为「请求来源 IP」，同步和异步样例均展示原始发起方 IP，缺失时显示「—」。

核对列表列名为「处理环节」，列表与抽屉阶段名称均采用本节定义，Stage 英文代码在抽屉展开后可见。正常异步完成记录显示「发布结果 · 成功 · 已发布」；ABIS 明确业务失败且失败响应已交付的记录显示「ABIS 处理 · 失败 · 已发布」。核对响应待发布、待人工核查和同步请求的环节选择仍符合各自的处理进展。

核对新增请求 `REQ-00000014` 和 `REQ-00000015`，列表共 15 条请求。分别打开指纹、人脸案例，核对候选数量为 3、默认选中第一名，并逐一切换三名候选，检查图像模态、指位、用户 ID、排名和分数与响应 JSON 一致。确认左侧待查图像始终可见，顶部业务结果摘要显示「查重成功 · 候选 3 条」。

核对信息表格第一行为请求 ID，接收时间和业务结果摘要通栏展示。异步两个耗时位于同一表格行；同步仅展示请求总耗时，省去响应发布状态。核对上下区域等宽、边缘对齐、间距以及标签栏和详情区的整体边框。

核对独立「接口报文」标签中的请求参数和响应结果默认均展开，能够分别折叠和重新展开。确认 JSON 格式化展示，长内容在各自的代码区域内滚动。核对多次调用的入参与响应按尝试对应，以及缺少正文时的提示。

用同步样例核对进入详情后直接可见三个 Event。用正常及异常异步样例核对三个顶层阶段默认展开，内嵌「ABIS 处理」默认折叠且显示状态和耗时。确认阶段行紧凑、状态及耗时对齐，并核对切换标签页后阶段和报文各自保留手动展开或折叠状态。

用内容较长的异步请求和较矮的窗口核对时间线高度随窗口调整。鼠标在时间线上滚动时，应能查看最后一条事件，顶部请求信息和标签栏仍可见。核对内容较少时自然显示。

核对页面内容区从筛选栏开始，顶部导航高亮「日志查询」。桌面宽度下六项筛选条件按 §1.8 排列为两行，同列的上下字段名和控件起点分别左对齐，查询和重置位于第二行最右侧。确认总耗时区间筛选已移除，日志列表仍显示「请求耗时」。检查完整 ID 和日期时间输入、下拉选项显示、窄屏换行，以及组合查询、重置和导出功能。按 §1.8 核对日志列表滚动前后筛选栏的位置，并验证滚动后可以直接展开日期选择器和下拉菜单、修改条件并重新查询。

核对筛选、列表与抽屉的查重接口类型均使用「1：N查重」，列表和抽屉能区分指纹与人脸。在 1422 × 804 和 1280 × 720 视口分别打开两个多候选案例，确认首屏无需滚动即可完整看到两张图像及图下用户 ID，候选分数和指纹指位可读。核对候选按钮仅显示序号，使用较长的候选用户 ID 时，按钮宽度保持稳定，完整 ID 可在对应图像下方查看。切换指纹候选时，右侧指位与对应图像一起更新。核对详情中已移除旧的单独业务处理耗时数值，导出 CSV 后确认表头和数据行均已去掉对应列。

## 2. 申请人列表界面

### 2.1 页面布局与列表

移除内容区独立的图标、「申请人列表」大标题和用途说明。顶部导航高亮「申请人列表」，内容区从筛选栏开始。桌面端将申请人 ID、首次注册时间范围、查询和重置排在同一行。筛选栏按 §1.8 的规则固定在顶部导航下方。

筛选栏下方显示申请人数量和范围说明「仅展示已确认注册成功且当前有效的申请人」。以当前有效的人脸注册记录作为申请人进入列表的条件，指纹允许缺采。

列表按「申请人 ID｜人脸｜指纹｜首次注册｜更新时间｜操作」排列。操作列只保留「查看详情」，两个时间列均支持排序。

### 3.4 验收要求

1. 打开顶部「监控」下拉菜单，核对样式和展开方式与「设置」一致。首次默认进入「服务状态」，可切换到「主机资源」，菜单标记当前项。在约 1024 px 视口核对导航内容完整、导航条无纵向滚动条。在约 624 px 视口核对横向滚动或折叠菜单可访问所有入口，监控和设置下拉菜单完整显示，当前页面高亮。
2. 核对服务状态共 5 个监控分组、10 项。默认上方为 3 张服务卡片，下方为 4 行数据存储表。汇总依次显示 10、8、1、1，「异常 1」的图标和数字用红色强调。确认 Gateway 未计入汇总。
3. 分别点击「全部」「正常」「异常」「未知」，核对可见项数为 10、8、1、1。「异常」只显示算法服务 1 的人脸服务，数据存储区隐藏。「未知」只显示数据存储区的 MinIO 行。恢复「全部」后，卡片和存储表恢复原布局。
4. 在 1024 × 900 的浏览器视口核对首屏可见全部三张卡片及存储表四行。再检查约 736 px、560 px 和 480 px 的监控内容容器，分别核对三列、两列加通栏、单列布局。确认算法服务 2 右侧没有因换列留下的空位，名称、IP 和状态标签可完整读取。
5. 核对数据存储四列对齐，PostgreSQL 与 MinIO 使用同一行样式。核对部署主机、IP、更新时间及「立即刷新」交互。页面只显示状态更新时间。
6. 切到「主机资源」，核对 8 台机器及两页对应的主机名和 IP。确认算法 VM 2 的资源显示「暂无数据」，其两个算法服务仍显示「正常」。
