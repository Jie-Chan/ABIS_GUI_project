# ABIS GUI 请求日志 Mock 开发说明

请在当前服务器的 GUI Mock 工程中完善现有日志页面。目前页面只展示单条请求的返回结果。本次将它扩展成**请求列表 + 右侧详情抽屉**，沿用工程现有的导航、组件和视觉风格，把已有的返回结果展示移入抽屉。

本次交付为可交互的前端 Mock，使用本地虚构数据。下文包含实现所需规则。

## 1. 请求列表

每个逻辑请求占一行。默认列表首行放**一条正常完成的请求**，下方把不同异常或边界场景各放一行。每个场景都能独立打开详情。

| 字段 | 展示规则 |
| --- | --- |
| 请求 ID `requestId` | 唯一标识逻辑请求。同一请求的 MQ 重投、调用尝试和发布重试归入同一行。 |
| 用户 ID `userId` | 被注册、识别或删除的业务对象 ID。未指定对象的 1:N 识别显示「—」，候选人 ID 不回填。 |
| 接口类型 | 至少覆盖 `enrollment`（注册）、`identification`（识别）、`delete`（删除）。同步与异步的同一操作使用相同类型。 |
| 接收时间 | 同步显示 ABIS 收到请求的时间，异步显示适配服务首次收到请求 MQ 消息的时间。 |
| 当前阶段 | 正常请求展示处理进展，异常请求突出需要关注的 Stage。 |
| 执行状态 | 展示请求进展或已确认的业务结果。执行结果不明时显示「待人工核查」。 |
| 响应发布状态 | 独立展示异步响应的发布进展，例如「待发布」「已发布」「暂无最终响应」。同步请求显示「—」。 |
| 请求耗时 | 已完成最终响应时显示总耗时。仍在处理、待核查或待发布时，显示从收到请求到当前的「已用时」。 |

列表支持按 `requestId` 或 `userId` 查找，并可叠加接口类型筛选。至少让同一个 `userId` 出现在两条不同请求中，方便验证查找效果。

## 2. 右侧请求详情抽屉

点击列表行，从右侧打开抽屉。关闭后保留列表原有的筛选条件和滚动位置。优先复用项目已有的 Drawer 组件。

- **顶部摘要**显示 `requestId`、`userId`、接口类型、接收时间、执行状态、响应发布状态和请求耗时。
- **主体默认展示 Stage 概览**。每个 Stage 显示名称、状态、起止时间和耗时。异常 Stage 需要容易定位。
- **点击 Stage 展开 Event**。每条 Event 显示动作、发生时间、结果、错误码和简短描述。多次投递或发布尝试在同一 Stage 下分开显示。失败后重试成功时，两次 Event 都保留。
- **现有返回结果**放在抽屉的结果区。样例有明确结果时展示结果。结果不明时显示「业务结果未确认」。

### Stage 与 Event 规则

| 链路 | Stage 显示顺序 |
| --- | --- |
| 同步 | `ABIS_RECEIVED` → `ABIS_PROCESSING` → `ABIS_RESPONDED` |
| 异步 | `ADAPTER_RECEIVED` → `ADAPTER_CALLING` → `ABIS_RECEIVED` → `ABIS_PROCESSING` → `ABIS_RESPONDED` → `ADAPTER_RESPONDED` |

上表是界面的逻辑顺序。实际时间允许重叠，例如 `ADAPTER_CALLING` 覆盖 ABIS 内部处理过程。

- `ADAPTER_RECEIVED` 在任务可靠保存时完成。请求 ACK 独立记录为 Event。
- `ADAPTER_CALLING` 在收到可解析的 ABIS 响应时正常完成，即使该响应明确表示业务失败。
- `ADAPTER_RESPONDED` 在响应通过约定路由、取得可靠发布确认且未被退回时完成。
- Stage 使用 `WAITING`、`RUNNING`、`SUCCESS`、`FAILED`、`UNKNOWN`。确定不会执行的阶段显示「不适用」。Event 使用 `STARTED`、`SUCCESS`、`FAILED`，表示当次动作的结果。
- 采集延迟时按已有证据展示，并提示「日志可能尚未齐全」。只有日志缺失时，保持已有判定。人工核查在本轮只做只读展示。

### 耗时口径

- **请求总耗时**：同步从 ABIS 收到请求到服务端完成响应发送。异步从适配服务首次收到请求 MQ 消息到最终响应获得可靠发布确认。
- **Stage 耗时**：从阶段首次开始到确认结束，包含阶段内的重试及等待。阶段完成后的重复投递或 ACK 异常不延长该阶段耗时。
- **ABIS 实际处理耗时**：取同一次 `ABIS_PROCESSING` 的起止时间。总耗时按请求自己的起止点计算，避免重复计入重叠阶段。缺少起止时间或结束早于开始时显示「无数据」。

## 3. Mock 样例

默认先展示一条完整的正常异步请求，方便对照六个 Stage。以下每个场景各用一条独立请求，分别验证，避免把多种异常叠在同一条样例里。

| 样例 | 打开抽屉后应看到 |
| --- | --- |
| **正常异步注册** | 六个 Stage 正常完成，业务结果成功，响应已发布，能核对总耗时与 ABIS 实际处理耗时。 |
| 同步入口校验拒绝 | 使用同步三阶段模板。入口失败，确定不会执行的业务处理 Stage 显示「不适用」。 |
| ABIS 明确返回业务失败 | 请求业务结果为失败。适配服务正常收到响应，因此 `ADAPTER_CALLING` 为 `SUCCESS`。 |
| 调用超时，执行结果不明 | 可用未指定对象的 1:N 识别作为样例，`userId` 显示「—」。超时 Event 为 `FAILED`，`ADAPTER_CALLING` 为 `UNKNOWN`，请求显示「待人工核查」，响应栏显示「暂无最终响应」。 |
| 落库后 ACK 异常，随后收到重投 | 列表仍只有一条请求。`ADAPTER_RECEIVED` 保持 `SUCCESS`，详情可展开查看 ACK 异常和重投 Event。 |
| 业务成功，响应发布失败待重试 | 执行状态为成功，响应状态为待发布，突出 `ADAPTER_RESPONDED`，耗时显示「已用时」。 |
| 业务成功，响应重试后发布成功 | 响应状态为已发布，`ADAPTER_RESPONDED` 为 `SUCCESS`。首次失败和后续成功分别可见。 |
| 响应消息被退回 | 即使收到 MQ 发布确认，该次发布仍按路由失败展示，响应保持待发布。 |
| 日志采集延迟 | 显示已有 Event 和「日志可能尚未齐全」提示。缺少结束时间的耗时显示「无数据」。 |

## 4. 交付验收

请在现有工程中完成页面，并实际打开预览检查以下交互：

1. 默认列表首行是正常请求，每条异常样例可独立打开。
2. 按 `requestId`、`userId` 查找和按接口类型筛选能组合使用。
3. 点击行打开右侧抽屉，展开 Stage 能看到对应 Event，关闭抽屉后保留列表上下文。
4. 同步和异步显示正确的阶段模板。业务失败、响应发布异常和待人工核查在界面上能够区分。
5. 重投和重试保留历史事件，并归在原请求下。

交付时提供修改的文件、页面预览入口，以及已实际验证的交互。
