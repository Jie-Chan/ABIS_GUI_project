# ABIS Mock 界面开发文档

版本日期 2026-11-11

## 1. 通用约定

请在当前服务器的 ABIS GUI Mock 工程中完善请求日志、服务状态监控和申请人列表三页。沿用现有页面入口、组件和视觉风格，使用本地虚构数据。请求日志与申请人列表共用按 `userId` 关联的业务数据。各页的展示规则和验收要求见对应章节。

## 2. 请求日志界面

日志页使用「请求列表 + 右侧详情抽屉」。人工核查在本轮只做状态和事件展示。

### 2.1 请求列表

每次接口调用对应一条逻辑请求，使用独立的 `requestId`，在列表占一行。默认先按 §2.3 展示异步的用户业务流程和独立异常，再展示同步正常样例。同一用户的注册、查重、删除按业务发生顺序排列，每行可独立打开详情。

| 字段 | 展示规则 |
| --- | --- |
| 请求 ID `requestId` | 该列仅显示 `requestId`，唯一标识逻辑请求。MQ 重投、调用重试和发布重试都归入原请求。 |
| 用户 ID `userId` | 被注册、识别或删除的业务对象 ID。Mock 的查重请求携带本次待查对象 ID。若客户接口约定允许省略 `userId`，GUI 显示「—」，可按 `requestId` 查找。命中的候选人 ID 留在响应详情。 |
| 接口类型 | 至少覆盖 `enrollment`（注册）、`identification`（查重）、`delete`（删除）。在同一列标明模态，例如「人脸注册」「指纹注册」「人脸查重」「指纹查重」。筛选仍按接口类型执行，例如筛选「注册」同时匹配人脸和指纹注册。 |
| 接收时间 | 同步取 ABIS 收到请求的时间，异步取适配服务首次收到请求 MQ 消息的时间。 |
| 当前阶段 | 优先显示此刻阻塞任务执行或响应交付的阶段。正常推进时显示实际进展最靠后的阶段。 |
| 执行状态 | 显示执行进展或明确业务结果。执行结果不明时显示「待人工核查」。 |
| 响应发布状态 | 异步显示「待发布」「已发布」或「暂无最终响应」。同步显示「—」。 |
| 请求耗时 | 完成最终响应时显示总耗时。处理、待核查或待发布时，显示从收到请求到当前的「已用时」。 |

支持按 `requestId` 或 `userId` 查找，并与接口类型筛选组合使用。列表和详情顶部使用同一套取值规则。同步请求从 ABIS 的「接收请求」Event 取 `userId` 和接口类型，异步请求从适配服务的「接收请求」Event 取值。异步请求的两条接收 Event 分别保留，ABIS 入口 Event 迟到时，列表和详情仍以适配服务入口的字段为准。

ACK 异常发生后，若 Worker 已开始调用 ABIS，当前阶段显示「调用 ABIS」。若响应发布失败正在等待重试，当前阶段显示「发布响应」，执行状态保留已确认的业务结果。响应重试成功后显示最后完成的阶段。若 ABIS 明确返回业务失败且失败响应已经交付，当前阶段显示「ABIS 处理」，执行状态显示「失败」。历史异常保留在抽屉中。

### 2.2 右侧详情抽屉

点击列表行，从右侧打开抽屉。关闭后保留筛选条件和列表滚动位置。顶部显示请求 ID、用户 ID、接口类型、接收时间、执行状态、响应发布状态、请求耗时和 ABIS 接口处理耗时。请求耗时和 ABIS 接口处理耗时并排展示。在抽屉顶部的信息表格中，于「执行状态」下方单独增加「业务结果摘要」一行，例如「查重成功 · 候选 0 条」。

| 链路 | 默认展示 |
| --- | --- |
| 同步 | 一个「ABIS 处理」Stage，代码为 `ABIS_HANDLING`。 |
| 异步 | 「适配服务接收请求」`ADAPTER_RECEIVED` →「调用 ABIS」`ADAPTER_CALLING` →「发布响应」`ADAPTER_RESPONDED`。展开「调用 ABIS」可查看适配服务的调用 Event 和内嵌的「ABIS 处理」。 |

抽屉使用「阶段概览」标题，保留顶层 Stage 卡片和纵向连线，按上表的业务顺序展示。顶层 Stage 默认折叠，各占一行，左侧显示阶段名称，右侧对齐状态和耗时。各 Stage 独立计时，时间可重叠。

展开任一 Stage 后，在 Event 时间线上方将阶段代码和起止时间放在同一行，例如 `ADAPTER_CALLING · 2026-11-11 15:14:43.017 → 15:14:43.227`。同一天只显示一次日期，跨天时起止时间均显示完整日期。保留毫秒精度，窄屏可换行。状态和耗时仍在阶段标题右侧。

#### Event 时间线

展开 Stage 后，在 Event 左侧显示发生时间，保留毫秒精度，并用纵向节点和连线按实际时间排列。正常 Event 尽量用一行展示时间、动作、结果或耗时，省略「本次动作已开始」「本次动作已确认完成」等重复说明。保留关键状态变化、失败原因和重试记录。多次投递、调用或发布在原 Stage 下按各次尝试分别展示。

调用和发布的开始事件用「发起第 1 次 ABIS 调用」「发起第 1 次响应发布」这样的动作名称，省略重复的「已开始」标签。调用尝试编号在对应尝试标题显示一次。MQ 发布确认事件显示「MQ 已确认发布」。

异步请求的「ABIS 处理」是对应调用尝试中一条紧凑、可展开的记录，按实际开始时间插入时间线。行内显示 ABIS 自身的状态和阶段耗时。正常调用时，这一行位于「发起 ABIS 调用」和「收到 ABIS 响应」之间。

~~~text
调用 ABIS                                  成功 · 210 ms
  15:14:43.007  ● 取得执行槽位并提交 CALLING · 本次调用前
  15:14:43.017  ● 发起第 1 次 ABIS 调用 · attempt-1
  15:14:43.027  ▸ ABIS 处理                 成功 · 180 ms
  15:14:43.227  ● 收到可解析的 ABIS 响应
~~~

#### ABIS 处理

「ABIS 处理」展开后显示三项 **接收请求 → 业务处理 → 发送响应**。业务处理开始和结束分别记录时间，界面合成一项展示。抽屉中的 ABIS 耗时指标统一使用「ABIS 接口处理耗时」。

#### 状态与重试

- Stage 用 `WAITING`、`RUNNING`、`SUCCESS`、`FAILED`、`UNKNOWN`。确定不会执行的阶段显示「不适用」。Event 用 `STARTED`、`SUCCESS`、`FAILED`，记录当次动作的结果。
- `ADAPTER_RECEIVED` 以任务可靠落库为完成点。请求 ACK 在接收阶段详情单独记录，正常发送事件标注「落库后」。ACK 发送异常后如果 MQ 重投，在同一请求下依次保留「ACK 发送异常」「重复投递」「发送请求 ACK」，接收 Stage 仍为 `SUCCESS`。
- Worker 有执行槽位后，将任务从 `PENDING` 原子更新为 `CALLING` 并提交，再开始调用。取得执行槽位并提交 `CALLING` 的 Event 标注「本次调用前」。`ADAPTER_CALLING` 的开始时间取首次实际开始调用尝试的 Event。确认请求未发出、故障可重试且仍有额度时，任务可退回 `PENDING`，调用 Stage 提示「待重试」。
- 请求可能已发出且结果不明时，`ADAPTER_CALLING` 显示 `UNKNOWN`，请求显示「待人工核查」，响应栏显示「暂无最终响应」。若随后采到 ABIS 内部日志，在内层按各自证据展示。
- `ABIS_HANDLING` 结束后按明确的 ABIS 业务结果判定。若业务失败但 ABIS 成功发出响应，`ABIS_HANDLING` 为 `FAILED`，「发送响应」Event 为 `SUCCESS`。适配服务收到可解析的响应后，`ADAPTER_CALLING` 为 `SUCCESS`。1:N 正常完成且候选列表为空时，按正常业务结果展示。
- `ADAPTER_RESPONDED` 在响应通过约定路由、获得 MQ 发布确认且未被退回后显示 `SUCCESS`，响应发布状态显示「已发布」。发布失败时按已知结果展示「待发布」或「待重试」。重试发送已保存的响应，详情保留各次发布结果。
- 日志采集延迟时提示「日志可能尚未齐全」。按已有证据展示状态，保留迟到的历史 Event。已确认的阶段成功状态保留。

#### 耗时

按 [[ABIS GUI 请求日志追踪模块设计方案#7.3 Stage 耗时统计与计算规则|设计方案 §7.3]] 计算。

| 指标 | 计算 |
| --- | --- |
| 同步请求总耗时 | ABIS 收到请求到服务端完成响应发送。 |
| 异步请求总耗时 | 适配服务首次收到请求 MQ 消息到最终响应通过约定路由并获得可靠发布确认。包含内部等待和重试。 |
| Stage 耗时 | 本阶段首次开始到确认结束，包含阶段内重试和间隔。 |
| 适配服务接收请求 | 适配服务收到请求 MQ 消息到任务可靠落库或确认已保存。 |
| 调用 ABIS | 首次开始调用尝试到收到可解析的 ABIS 响应，包含等待本地 HTTP 连接。 |
| 发布响应 | 开始保存待发布结果到获得 MQ 可靠发布确认。 |
| ABIS 接口处理耗时 | `ABIS_HANDLING` 的阶段耗时，从 ABIS 收到请求到服务端完成响应发送，包含入口处理、业务处理和响应发送。 |

使用 Event 发生时间。各 Stage 时间可以重叠，请求总耗时按请求自身的起止点独立计算。已结束指标缺少起止点或时间顺序无效时显示「无数据」。

#### ABIS 接口响应

在抽屉最底部保留「ABIS 接口响应」区，打开抽屉即在标题下直接显示格式化 JSON，移除「查看响应」按钮及额外的展开步骤。若同一请求有多份实际响应，按尝试编号和响应时间区分。没有已记录的正文时显示「暂无 ABIS 响应内容」。Stage 内的「发送响应」Event 展示发送时间、状态和异常信息。

### 2.3 Mock 样例

默认按下面的顺序展示，共 13 条请求。每行使用独立的 `requestId`。同一用户的多次接口调用使用同一个 `userId`，并记录人脸或指纹模态。样例按业务发生顺序展示。

#### 异步业务流程

| 顺序 | 用户 ID | 模态 | 接口 | 展示与核验 |
| --- | --- | --- | --- | --- |
| 1 | `U001` | 人脸 | 注册 `enrollment` | 人脸注册成功，响应已发布。可展开「调用 ABIS」下的「ABIS 处理」和三项 Event，并在抽屉底部查看成功响应。 |
| 2 | `U001` | 指纹 | 注册 `enrollment` | 指纹注册成功，响应已发布。该用户的人脸和指纹均已注册成功，申请人列表可显示 `U001`。 |
| 3 | `U001` | 人脸 | 查重 `identification` | 人脸查重成功，候选列表为空。 |
| 4 | `U001` | 指纹 | 查重 `identification` | 指纹查重成功，候选列表为空，业务流程完成。 |
| 5 | `U002` | 人脸 | 注册 `enrollment` | 人脸注册成功，响应已发布。 |
| 6 | `U002` | 人脸 | 查重 `identification` | 查重成功，命中已有用户 `U001`。列表的用户 ID 为待查对象 `U002`，响应详情可看到候选人 `U001`。 |
| 7 | `U002` | 人脸 | 删除 `delete` | 删除本次新注册的 `U002`，显示删除成功。已有用户 `U001` 仍是查重候选人。 |
| 8 | `U003` | 人脸 | 注册 `enrollment` | 等待 ABIS 响应超时且结果不明。当前阶段为「调用 ABIS」，执行状态为「待人工核查」，暂无最终响应。该用户的流程停在注册，列表只有这一条请求。 |

#### 异步查重异常

以下用户使用已有注册成功的预置数据，每个用户只展示一条本次查重请求。

| 顺序 | 用户 ID | 模态 | 接口 | 展示与核验 |
| --- | --- | --- | --- | --- |
| 9 | `U004` | 人脸 | 查重 `identification` | 任务落库后 ACK 发送异常，随后收到 MQ 重投。接收 Stage 保持 `SUCCESS`，查重照常推进。列表只有一条请求，详情保留 ACK 异常、重复投递和本次发送 ACK。 |
| 10 | `U005` | 指纹 | 查重 `identification` | 获取 HTTP 连接超时，已确认本次请求未发出。「调用 ABIS」显示「待重试」，详情记录失败原因及未发送的判定依据。 |
| 11 | `U006` | 人脸 | 查重 `identification` | ABIS 明确返回查重失败，失败响应已交付。列表当前阶段为「ABIS 处理」。内层为 `FAILED`，发送响应 Event、外层「调用 ABIS」和「发布响应」为 `SUCCESS`。抽屉底部可查看失败响应正文。 |
| 12 | `U007` | 指纹 | 查重 `identification` | ABIS 查重成功，响应发布失败并等待重试。执行状态为成功，当前阶段为「发布响应」，响应状态为「待发布」，请求耗时显示「已用时」。 |

#### 同步正常样例

| 顺序 | 用户 ID | 模态 | 接口 | 展示与核验 |
| --- | --- | --- | --- | --- |
| 13 | `U008` | 人脸 | 删除 `delete` | 同步删除成功。顶层只显示一个「ABIS 处理」，展开可见接收请求、业务处理、发送响应。响应发布状态为「—」，抽屉底部可查看成功响应正文。 |

用 `REQ-00000001`（`U001` 人脸注册）校验耗时。以适配服务收到请求 MQ 消息为 `0 ms`，`20 ms` 可靠落库，`25 ms` 发送 ACK，`50 ms` 取得执行槽位并提交 `CALLING`，`60 ms` 发起调用，`270 ms` 收到可解析的 ABIS 响应，`280 ms` 开始保存待发布结果，`320 ms` 获得最终响应发布确认。ABIS 在 `70 ms` 收到请求，`250 ms` 完成响应发送。

抽屉顶部预期显示「请求总耗时 `320 ms`」和「ABIS 接口处理耗时 `180 ms`」。阶段概览依次显示 `20 ms`、`210 ms`、`40 ms`。三个顶层阶段之间的 `40 ms` 和 `10 ms` 计入请求总耗时。

### 2.4 日志页面验收

1. 实际打开 GUI 日志入口。默认依次展示 `U001` 至 `U003` 的异步业务流程、`U004` 至 `U007` 的异步查重异常、`U008` 的同步样例，共 13 行。
2. 按 `userId` 分别查询 `U001`、`U002`、`U003`，核对返回 4 条、3 条、1 条请求。核对 `U001` 的顺序为人脸注册、指纹注册、人脸查重、指纹查重。`U002` 的查重候选人为 `U001`，删除对象为 `U002`。验证 `requestId` 查找、接口类型筛选和 `userId` 缺失时的展示。核对 `REQ-00000003` 的请求 ID 单元格仅显示编号，打开抽屉后，核对顶部信息表格中「执行状态」下方的「业务结果摘要」行显示「查重成功 · 候选 0 条」。
3. 打开 `REQ-00000001`，核对顶部耗时 `320 ms` 和 `180 ms`，以及阶段概览默认折叠且按业务顺序显示三行，各行耗时依次为 `20 ms`、`210 ms`、`40 ms`。展开后核对桌面宽度下阶段代码和起止时间同一行展示，以及事件顺序和毫秒精度。检查同日和跨日的日期格式、窄屏换行，以及 ACK 的「落库后」和提交 `CALLING` 的「本次调用前」标注。「ABIS 处理」位于对应尝试的发起调用和收到响应之间，展开可查看三项 Event。
4. 滚动到抽屉底部，确认响应正文直接显示为格式化 JSON。另核对有多份响应和暂无响应正文时的展示。关闭抽屉后核对筛选条件和列表滚动位置。
5. 核对 `U004` 至 `U007` 的异常与重试展示、`U008` 同步样例的单一 Stage 和响应正文，以及两种链路的入口字段取值。

## 3. 服务状态监控界面

更新 GUI Mock 的「服务状态监控」页面和对应数据。默认按实际部署显示 5 组、10 个实例或服务，全部展开。每个实例或服务单独占一行，显示名称或实例 ID 及当前状态。

### 3.1 监控对象

| 分组 | 数量 | Mock 展示项 |
| --- | ---: | --- |
| ABIS-System | 2 | `system-1`、`system-2` |
| 算法服务 1 | 2 | 人脸服务 `face-1`、指纹服务 `fingerprint-1` |
| 算法服务 2 | 2 | 人脸服务 `face-2`、指纹服务 `fingerprint-2` |
| PostgreSQL | 3 | `postgresql-1`、`postgresql-2`、`postgresql-3` |
| MinIO | 1 | `minio-1` |

移除旧 Mock 中的 ABIS Gateway。人脸和指纹按各自所属的算法服务分组展示。

### 3.2 状态汇总与筛选

- 页首按实例和服务统计「全部」「正常」「异常」「未知」。四项均可点击筛选，默认选中「全部」。筛选后只显示匹配的行，并隐藏没有匹配项的分组。
- 取得明确的监控结果后显示「正常」或「异常」。暂时取不到状态时显示「未知」，该实例仍计入总数，可在「全部」和「未知」中查看。
- Mock 样例为 8 项正常、1 项异常、1 项未知。算法服务 1 的人脸服务为「异常」，MinIO 实例为「未知」，其余为「正常」。

### 3.3 时间与布局

- 页首时间信息显示为「状态更新于 YYYY-MM-DD HH:mm:ss」，取最近一次成功获取监控状态的时间。移除「每 60 秒自动刷新」以及刷新频率、倒计时和接口调用方式的说明。
- 沿用项目已有的组件、配色和字体。分组卡片使用浅底、统一样式和细分隔线，各行的状态标签右对齐。桌面宽度下优先采用上三下二布局，窗口缩窄时自动换列。
- 使用绿色、红色、灰色文字标签分别表示「正常」「异常」「未知」。红色集中用在异常行的状态标签上，方便定位具体实例。

### 3.4 监控页面验收

1. 打开「服务状态监控」入口，核对默认视图为 5 组、10 项。两套算法服务各显示一项人脸和一项指纹，PostgreSQL 显示 3 个实例，MinIO 显示 1 个实例。
2. 分别点击「全部」「正常」「异常」「未知」，核对显示项数为 10、8、1、1。「异常」定位到算法服务 1 的人脸服务，「未知」定位到 MinIO 实例。
3. 核对页首的状态更新时间，以及刷新频率、倒计时和接口调用方式已从界面移除。缩窄窗口，检查实例名称和状态标签是否重叠或截断。

## 4. 申请人列表界面

### 4.1 数据与展示规则

请求日志和申请人界面按 `userId` 共用一份 Mock 数据。申请人列表展示已确认注册成功、当前有效的申请人，每个用户占一行。注册成功以 ABIS 的业务结果为准。双模态正常样例 `U001` 在人脸和指纹注册都成功后才显示为一名申请人，查重是后续请求。`U003` 只出现在请求日志中。`U004` 至 `U007` 使用同一份数据里预置的已注册申请人。按当前有效申请人的口径，`U002` 和 `U008` 的删除成功后从申请人列表移除，历史请求仍可在日志查询。

- 列表和详情抽屉读取同一份当前有效入库记录，人脸和指纹数量分别按有效记录统计。申请人 ID 对应日志中的 `userId`，全程按完整字符串处理，保留可能存在的前导零。
- 首次入库时间取首次确认注册成功的时间。最近更新时间取最近一次成功改变入库数据的时间。查重和失败的入库调用保留在请求日志中，当前入库数量、图像及最近更新时间沿用此前的有效数据。
- 入库记录包含 `userId`、记录 ID、模态、更新时间和对应图像。指纹记录同时包含指位。能够确认具体入库请求时，记录关联该请求的 `requestId`。

### 4.2 列表、筛选和日志入口

- 列表显示申请人 ID、人脸入库、指纹入库、首次入库时间、最近更新时间和操作。人脸、指纹两列按各自的有效记录显示「已入库」及条数，或显示「未入库」。
- 支持按完整申请人 ID、入库模态和首次入库时间范围组合查询。入库模态选项为「全部」「仅人脸」「仅指纹」「人脸和指纹均已入库」。首次入库时间和最近更新时间均支持排序。
- 每行操作列提供「查看详情」「查看日志」。查看详情打开该申请人的抽屉。**申请人级「查看日志」入口只放在列表行的操作列。**
- 点击「查看日志」时，日志页自动填入完整 `userId` 并执行查询，清除上次查询遗留的筛选条件。如果日志页必须传时间范围，初始化为能覆盖该申请人 Mock 日志的范围，并在筛选区显示。从日志页返回时，恢复申请人列表的筛选、排序、页码和滚动位置。

### 4.3 申请人详情抽屉

- 顶部显示申请人 ID、首次入库时间和最近更新时间。下方按「人脸」「指纹」分组，分组标题显示各自的记录数量。
- 人脸展示对应入库记录的缩略图。指纹按左手、右手和实际指位排列。指位缺失时显示「指位未标注」。同一指位有多条记录时，可在该指位内切换。
- 点击缩略图可放大，并查看该图对应的记录 ID、更新时间及指位（适用于指纹）。Mock 使用每条入库记录绑定的本地样例图像，缩略图和放大图对应同一条入库记录。
- 模态或指位没有入库记录时显示「未入库」。有记录但图像缺失或加载失败时显示「图像不可用」，保留记录信息。
- 去掉抽屉底部的「查看该申请人日志」按钮。如果入库记录有明确的 `requestId`，且日志页支持定位该请求，可在图像详情提供「查看本次入库日志」。

### 4.4 Mock 样例

样例使用 §2.3 的 `userId` 和既定日志。入库记录、图像和指位配置在同一套 Mock 数据中。

| 申请人 ID | 当前入库状态 | 核验场景 |
| --- | --- | --- |
| `U001` | 人脸 1 条、指纹 10 条 | 按 §2.3 的人脸、指纹注册结果配置样例图像。首次入库时间取人脸注册成功时间，最近更新时间取指纹注册成功时间。后续两次查重仅增加日志。 |
| `U004` | 仅人脸 | 使用预置的人脸入库记录及图像。抽屉显示指纹未入库，日志可查已有的 ACK 异常和重投流程。 |
| `U005` | 仅指纹 | 使用预置的指纹入库记录。一个指位配置两条带不同图像的记录，另一个指位配置一条图像不可用的有效记录。日志仍为 §2.3 的待重试查重请求。 |
| `U006` | 预置人脸入库 | 验证明确的查重失败有对应日志，当前入库数量、图像和最近更新时间沿用预置数据。 |

### 4.5 申请人页面验收

1. 在列表按完整 ID 查询 `U001`，确认只有一行，列表和抽屉均为人脸 1 条、指纹 10 条，首次入库时间和最近更新时间对应两次成功注册。
2. 从 `U001` 的列表行点击「查看日志」，核对日志页自动按 `userId` 显示 4 条请求。返回时核对列表的筛选、排序、页码和滚动位置。核对 `U006` 的失败日志可见，当前入库记录及时间与预置数据一致。
3. 打开 `U001`、`U004`、`U005` 的详情，验证缩略图、放大图、记录 ID、更新时间和指位一一对应。验证同一指位的多条记录可切换，并分别验证「未入库」和「图像不可用」。
4. 核对三种入库模态筛选、首次入库时间范围和两个时间字段的排序。确认 `U003` 待核查时只出现在日志，`U002`、`U008` 删除成功后只可在日志查看历史。
5. 确认申请人级「查看日志」只在列表行的操作列出现。如实现「查看本次入库日志」，核对该入口按 `requestId` 定位具体请求。

交付时一并给出 Mock 启动方式和可复查的样例 `userId`。
